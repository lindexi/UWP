# CBus 重构经验文档

## 1. 最重要的经验

最初将客户端连接能力与宿主监听能力放在同一个类库里，会导致职责边界模糊：

- 客户端只需要连接与发现，却被迫依赖宿主内部的注册与分发模型。
- 宿主需要发布监听地址，却没有清晰的可运行入口项目。
- 单元测试难以区分客户端行为与宿主行为。

本次重构后，核心经验是：**先拆边界，再补实现**。

## 2. 本次拆分收益

### 2.1 对 NuGet 包更友好

`CBus` 类库现在只暴露以下稳定概念：

- 请求与响应消息
- 路由定义
- 消息序列化
- HTTP/Pipe 连接器
- 终结点发现

这些能力更适合被客户端和服务安装程序复用。

### 2.2 对宿主进程更友好

`CBus.Host` 现在集中承载：

- 服务注册
- 请求分发
- HTTP/Pipe 监听适配
- 地址发布
- 可执行入口

宿主侧职责集中后，后续接入真实网络监听或系统服务托管会更直接。

### 2.3 对测试更友好

通过把传输、注册表和文件系统抽象出来：

- 客户端测试不依赖真实网络。
- 发现能力测试不依赖真实注册表和磁盘。
- 宿主测试可以直接验证发布、分发和监听适配逻辑。

## 3. 设计取舍

### 3.1 为什么保留共享消息模型

无论是客户端还是宿主，都会使用：

- `CBusRequest`
- `CBusResponse`
- `CBusMessageSerializer`
- `CBusRouteDefinition`

这些类型属于协议层，应留在公共类库中，避免重复定义。

### 3.2 为什么将注册与分发迁移到宿主

服务注册表、分发器和监听器本质上都是宿主内部实现细节，客户端不需要感知这些概念。把它们留在公共类库中会扩大 API 面并增加理解成本。

### 3.3 为什么使用传输与存储抽象

网络、命名管道、注册表和文件系统都是外部依赖，使用最小抽象可以：

- 保持单元测试稳定。
- 降低平台差异影响。
- 允许宿主与客户端在不同环境下替换具体实现。

## 4. 后续建议

- 在 `CBus.Host` 中继续接入真实 HTTP 监听与命名管道实现。
- 为发现机制增加版本号和健康状态。
- 为地址发布增加过期时间与清理策略。
- 为宿主引入更清晰的服务生命周期管理。
- 在客户端补充默认 HTTP 传输实现。
