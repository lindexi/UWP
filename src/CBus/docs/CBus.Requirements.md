# CBus 需求分析

## 1. 背景与目标

CBus 提供一个位于服务与客户端之间的中间平台层，用于在多个应用和服务之间建立统一的通信与路由能力。其设计参考 d-Bus 思想，但消息模型采用 HTTP 1.1 结构，以便统一 Header、Body、状态码与路由路径等概念。

目标如下：

- 提供统一的消息模型，兼容 HTTP 风格的 Header 与 Body。
- 支持两种连接方式：`HTTP` 与 `Pipe`。
- 允许服务通过安装期配置或运行期 API 完成注册。
- 允许客户端通过路径直接发起请求，由 CBus 完成路由分发。
- 为后续日志、统计和禁用策略预留能力。

## 2. 角色分析

### 2.1 CBus 核心

职责：

- 管理服务注册信息。
- 维护可路由的 API 路径集合。
- 接收客户端请求并根据路径分发。
- 为不同连接方式提供一致的请求与响应抽象。
- 记录调用元数据，供后续统计与治理使用。

### 2.2 服务端

职责：

- 提供一个或多个 API 路径。
- 提供进程启动路径与启动参数。
- 在安装期通过配置文件注册，或在运行期调用注册 API。
- 响应来自 CBus 分发的请求。

### 2.3 客户端

职责：

- 使用路径发起请求。
- 可通过 HTTP 或 Pipe 方式连接 CBus。
- 接收最终由目标服务返回的响应内容。

## 3. 核心业务流程

### 3.1 服务安装期注册

1. 服务在约定目录中写入注册配置。
2. CBus 读取配置文件。
3. CBus 校验配置合法性。
4. CBus 加载服务进程路径、参数与路由路径。
5. CBus 将该服务加入注册表。

### 3.2 服务运行期注册

1. 服务启动。
2. 服务调用 CBus 提供的注册 API。
3. CBus 校验注册请求。
4. CBus 更新或补充服务注册信息。
5. CBus 将该服务标记为可路由目标。

### 3.3 客户端请求分发

1. 客户端构造 HTTP 1.1 风格请求。
2. 客户端通过 HTTP 或 Pipe 将请求发送给 CBus。
3. CBus 解析请求路径。
4. CBus 根据路径第一节定位目标服务。
5. CBus 将请求转发到目标服务。
6. 服务返回响应。
7. CBus 将响应回传给客户端。

## 4. 功能性需求

### 4.1 消息模型

CBus 的消息模型需要满足以下要求：

- 请求与响应均采用 HTTP 1.1 风格结构。
- Header 使用 Key-Value 集合表示。
- Body 支持任意文本或二进制内容。
- 请求至少包含方法、路径、Header、Body。
- 响应至少包含状态码、原因短语、Header、Body。

### 4.2 连接方式

#### 4.2.1 HTTP 连接

- 支持标准 HTTP 请求语义。
- 支持后续扩展 HTTPS。
- 使用统一消息模型，不在 API 设计层暴露传输细节差异。

#### 4.2.2 Pipe 连接

- 用于本机 IPC 场景。
- 管道中传输的数据格式仍为 HTTP 1.1 风格消息。
- 对上层调用者暴露与 HTTP 一致的发送接口。

### 4.3 服务注册

#### 4.3.1 配置注册

注册配置至少包含：

- 服务名称。
- 进程启动路径。
- 启动参数列表。
- 服务可直接路由的 API 路径集合。

#### 4.3.2 API 注册

运行期注册接口至少支持：

- 注册服务基础信息。
- 注册路由路径。
- 合并安装期与运行期信息。

### 4.4 路由规则

- 路径必须以 `/` 开始。
- 路径第一节为服务根标识。
- 路径第一节必须全局唯一。
- 相同服务可注册多个路径。
- 若请求路径未命中任何服务，应返回未找到结果。

### 4.5 端口发现

README 提出默认使用 `3323` 端口，并在本机文件夹与注册表中写入监听端口。当前阶段需求分层如下：

- API 设计中保留默认端口常量与发现结果模型。
- 具体文件系统与注册表集成可作为后续基础设施扩展。
- 非 Windows 环境不依赖注册表。

### 4.6 日志与治理预留

当前阶段至少应保留以下可扩展点：

- 记录请求路径。
- 记录请求次数。
- 标记路径是否被禁用。

本轮实现不要求完整日志系统，但核心模型应允许承载此类元数据。

## 5. 非功能性需求

### 5.1 可测试性

- 核心路由逻辑不依赖具体网络传输。
- 连接器通过统一接口或统一消息模型进行测试。
- 服务注册、路径冲突、请求编解码等逻辑必须可单元测试。

### 5.2 可扩展性

- 允许未来增加更多传输类型。
- 允许未来增加证书、注册中心、日志上报、禁用策略等模块。
- 核心 API 应尽量围绕消息、路由、服务注册等稳定概念设计。

### 5.3 兼容性

- 当前项目目标框架为 `net10.0`。
- 设计应尽量避免绑定 UWP 专属能力，以便保持核心类库独立。

### 5.4 健壮性

- 参数为空、路径格式错误、重复路由等情况应给出明确错误。
- 对二进制消息体不得做隐式编码假设。
- 路由查找失败时应返回可诊断的结果。

## 6. 关键约束与设计决策

- 本轮实现优先完成核心类库内存模型与逻辑，不直接实现真实网络监听。
- HTTP 与 Pipe 连接器先实现统一的消息编解码与模拟发送能力。
- 服务转发逻辑先通过内存注册表与处理委托表达。
- 配置文件读取、注册表写入、进程拉起不在本轮实现范围内，但需在文档中留出接口位置。

## 7. 验收标准

本轮交付满足以下条件：

- 文档目录包含需求分析文档。
- 文档目录包含 API 设计文档。
- 类库中存在清晰的请求、响应、服务注册、路由注册、连接器 API。
- 存在单元测试项目。
- 单元测试覆盖：
  - 路由路径合法性校验。
  - 路由根段唯一性校验。
  - 服务注册成功与冲突失败。
  - 请求分发成功与未命中返回。
  - HTTP/Pipe 消息编解码一致性。
- 解决方案可构建通过。

## 8. 本轮暂不实现的内容

- 真实 HTTP 监听与 HTTPS 证书处理。
- 真实命名管道传输。
- 注册表读写与端口文件落盘。
- 自动拉起外部服务进程。
- 完整日志上报与治理后台联动。
